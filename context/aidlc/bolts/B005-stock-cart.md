## Fixture and contract decisions approved in revision 1

The user approved these choices under AUTH-009. They refine the synthetic profile without selecting merchant policy. The exact implemented surface is in [local contracts](../../../backend/readiness/11-local-stock-cart-contracts.md). The audit-triggered dependency repair is recorded below; no commerce behavior changed.

| Concern | Proposed behavior / rationale |
| --- | --- |
| Stock authority | One active sellable TEST-WH. Available = sellable_on_hand minus reserved_quantity, never negative. B005 changes sellable quantity only; reserved delta stays zero. No caller can write counters, movement result balances or reservation/allocation state directly |
| Stock permission / threshold | Add fixed local inventory.manager role with inventory.read and inventory.adjust, assigned through existing access administration. Catalog roles cannot adjust stock; access managers do not implicitly gain stock permission. Integer nonzero adjustment, absolute delta at most 1,000 units per command; larger adjustments rejected. This is a per-command synthetic safety bound, not a cumulative/high-value approval workflow. Bounded reason code/note required; no personal data in notes |
| Opening stock | Deployment-only fixture establishes TEST-WH/zero position and invokes the same attributed, audited movement command using an authorized synthetic stock operator and stable operation key. This is an explicit local fixture substitute for the future approved import-job opening path in T05/BUILD-032; no CSV/import workflow or counter overwrite |
| Guest capability | Server generates 256 random bits, returns the raw capability once over the local no-store creation response, and stores only a cryptographic hash. Send capability in a dedicated redacted header, never a URL. Guest creation has no replay snapshot containing the token; after a lost issuance response a caller may create a new empty cart, with the inaccessible one expiring. All subsequent mutations use scoped idempotency. No token recovery, guest order capability, authentication-provider change or public deployment |
| Cart ownership / expiry | Exactly one customer or guest owner. One active cart per customer in the fixed local channel; concurrent get/create returns that cart. Guest capability is cart-specific and grants no customer access. Apply the existing 30-day inactivity duration to local carts, refresh activity on successful mutations, and reject expired/merged carts for fresh commands. Request-time terminalization and replacement retain historical rows; no purge/sweep job |
| Cart item operations | Add increments an existing variant line; change replaces its quantity; remove deletes that line; clear removes owned active lines. Require expected cart version and scoped Idempotency-Key for mutations; version/idempotency keep retries from adding twice. Quantities 1–20, at most 50 distinct lines; use any stricter existing SKU cap without adding policy administration. Reject fractional/overflow/unknown fields and caller-supplied ownership, prices, totals or stock |
| Observed price / stock | Store exact minor-unit observations and return current observations plus explicit changed/unavailable warnings. No shipping/tax/discount/payable quote. Merchandise estimates are exact decimal strings; missing current prices make the complete estimate unavailable. Existing unavailable lines remain visible/removable, never silently dropped. New adds/quantity increases require currently eligible published variants/current prices; zero available stock is explained but cart intent does not reserve stock or guarantee purchase |
| Deterministic merge | Require current customer identity plus guest capability and expected source/target versions. Lock carts in UUID order. Union lines by variant; sum duplicates and clamp to 20 or an existing lower SKU limit, returning requested/accepted quantities and reason for every clamp. If the union exceeds 50 lines, return a conflict and leave both carts unchanged. Preserve unavailable existing lines with warnings. On success target stays customer-owned, source becomes terminal merged and cannot accept fresh commands; do not transfer raw capabilities or silently discard lines |
| Replay / authority | Scope by surface, verified actor, operation and key; hash canonical payload including versions/cart IDs. Recheck current customer/staff status or guest capability before replay. Changed payload conflicts. Successful merge retry by the same authorized customer may replay the original result for its matching terminal source; terminal source rejects new keys. Replay does not extend expiry or revive a cart. Persist bounded deterministic errors; unknown COMMIT returns uncertainty and resolves through an exact caller retry, never automatic duplicate effects |
| Guest audit boundary | Existing generic audit supports staff/customer actors only. Inventory always writes staff audit. Guest cart commands use protected scoped outcomes and safe operational correlation; do not fabricate a staff/customer actor or broaden generic audit with system/guest actors in this Bolt. No cart consumer/destination is required for current behavior; stock alone extends the existing pending event route |
| HTTP surface | Under /api/v1: staff inventory position/ledger reads and /staff/inventory/adjustments; /customer/cart, /customer/cart/items, item change/remove and /customer/cart/merge, with a guest creation operation. Exact operation IDs and schema examples are recorded before coding. Existing 428 missing/412 stale version, ownership-hidden 404, permission 403, bounded conflict/validation errors and 503 dependency failures apply. Raw counts/ledger stay staff-only; public/owned catalog observations reveal indicative stock only |
